# 學習單內容校正規則

## 適用範圍

本規則用於已完成初稿的學生版學習單。校正目的是讓既有內容更清楚、可執行並符合目標客群；不重新設計教材，不核對資料庫的情境問題或引導目標。

學生版不得混入輔導員觀察、假設、追問、支持策略或診斷式歸因。

## 可直接修正

以下變更不影響原意時可直接套用：

- 錯字、標點、空格、異常換行及重複編號。
- 同一層級用詞、稱呼與句型不一致。
- 明確可判斷的單選／複選標示錯誤。
- 選項語法不平行，例如同一組混用「我很滿意／普通／我不滿意」。
- 冗字、重複語句及不改變意思的語序調整。
- 「其他」選項與自由填答標記的格式統一。
- 依格式契約將既有舉例改為獨立灰字行，或將既有 AI 提示說明統一為單行提示框；不改變舉例、提示語或題目的原意。
- AI 提示說明可移除句尾句號，並讓後方既有的提示語引用框使用 Script 提供的一鍵複製按鈕；不新增或刪除提示語內容。

## 必須確認

以下變更可能改變教材內容，先提出待確認事項，不直接套用：

- 新增、刪除或合併題目。
- 改變單選、複選、矩陣或自由填答題型。
- 新增、刪除或實質改變選項。
- 改變問題原意、價值立場或學生要做的決定。
- 加入原稿沒有提供的知識、建議或風險判斷。

## 明確性

每個題目都要通過：

1. 一個指令只要求一個主要動作。
2. 明確使用「勾選、單選、排序、填寫、記錄」等動詞。
3. 「這個、上述、它」等指稱能找到唯一對象。
4. 題目與選項使用同一敘述角度及相近語法。
5. 抽象詞或專有名詞改為客群熟悉的日常說法；無法簡化時提供短例子。
6. 不看影片仍能理解題目要如何作答。

## 可執行性

每個題目都要通過：

1. 學生看完指令後知道要留下哪一種答案。
2. 單選、複選、短答與長答有明確標記。
3. 開放題有具體標籤、提示或句型；不只留下無標示空白。
4. 行動題至少包含可觀察的動作與對象；只有在任務需要時才加入時間或完成條件。
5. 不要求學生取得題目未提供、也不一定擁有的資料。
6. 選項可區分且足以作答；不為湊數加入意思重疊的選項。

## 客群適切性

- 本批學習單的共同客群已確認為「台灣大專生與初入職場者」；`audience` 必須以此文字記錄在 Markdown frontmatter。未來若另有指定客群，以該次明確指定為準。
- 客群適切性的核心驗收條件是「低認知負擔」與「高可執行性」：學生能快速理解題意、辨認作答方式，並知道第一步要做什麼。
- 使用台灣繁體中文及符合客群生活經驗的用語。
- 降低閱讀與工作記憶負荷，但不使用幼兒化稱呼或過度可愛語氣。
- 不預設學生理解專業、法律、醫療或輔導術語。
- 不把回答直接解釋為人格、缺陷、心理狀態或診斷結果。

### 降低認知負擔與提高可執行性

編輯時須考量情緒障礙、自閉症特質使用者可能有不同的閱讀、情緒負荷與執行需求，不預設每位使用者都有相同困難。以下是共同的內容難度調整，不是診斷或個別支持方案。學生版 Markdown（含 frontmatter）、HTML、填答提示與列印成品不得出現障礙、診斷或「特殊版本」等客群標籤；只呈現調整後的題目。

1. **一句一個重點。** 將過長指令拆成短句；原題已有多個步驟時，可依執行順序分行說明，但保留同一題、原作答欄位及所有要求。
2. **把動作說清楚。** 讓學生看得出要勾選、填寫或記錄什麼。沿用原題已指定的數量、對象、時間與條件；不得為了具體化而自行新增限制。
3. **減少來回找資訊。** 將既有作答說明放在對應題目前，指稱改成可辨認的名稱；避免要求學生同時記住跨段的多項條件。
4. **使用直接、日常的表達。** 減少雙重否定、隱喻、反諷與含糊詞。保留關鍵概念；若改成日常說法會失去原意，列為待確認。
5. **保持一致與可預期。** 相同事物用相同名稱，同組選項保持同一視角及句型；明確區分題目、說明與填答位置。
6. **降低評價壓力。** 用中性、尊重成年人的語氣，避免責備、羞辱、催促或把回答推論成個人缺陷。若原題本身包含需改變的價值判斷，先列為待確認，不直接更換立場。
7. **讓行動能開始。** 行動題須能辨認第一個可做的動作與對象；可把原有行動說清楚，不自行加入新行動、承諾、時限或達成門檻。
8. **提示不代替答案。** 可補充純作答格式，例如日期格式；內容例子僅能整理原稿已提供的資訊，不加入新知識、建議或暗示學生應選的答案。

降低難度不得以刪題、合併題目、減少選項、改變題型或刪除重要條件達成。若需要「不確定」「不適用」「暫時跳過」等原稿沒有的選項或作答規則，依「必須確認」處理。

### 修改判斷範例

| 情況 | 可直接處理 | 需先確認的界線 |
|---|---|---|
| 指令太長 | 同一題內拆成短句，保留原要求 | 拆成新增題目或作答欄位 |
| 「這個目標」指稱不清 | 改成「上一題選擇的工作目標」；須能唯一對應 | 原稿有多個可能目標，不能自行選定 |
| 日期欄不清楚 | 保留原期限語意，補日期填寫格式 | 新增「本週內」等期限 |
| 行動太抽象 | 用原稿已有的動作、對象改寫 | 加入原稿沒有的行動方案 |
| 選項太多或太相似 | 統一語法與排版，保留選項意思 | 刪除、合併或實質改變選項 |

### 依任務補充時間資訊

時間提示在 Correct 階段依題意寫入標籤，保留「預計、實際、開始、完成」的原意。只補任務需要的精度，不要求所有題目都填完整日期、時刻與週期。

| 原題任務性質 | 可補充的填寫格式 |
|---|---|
| 一次性事件或完成日期 | 年／月／日 |
| 預約、會面等需要明確時刻的任務 | 年／月／日、幾點幾分 |
| 原題已要求重複執行或安排頻率 | 每幾天／週／月一次，或每週幾次；依原題選擇適合的單位 |
| 原題已要求記錄投入時間 | 幾分鐘或幾小時 |
| 原題已要求記錄一段期間 | 開始及結束日期，或持續幾天／週；依原題保留對應形式 |

補充格式不代填具體日期、期限、頻率或時長。新增原題未要求的時間欄位、固定期限或執行次數，仍須確認；任務性質不明時先確認，不由 Script 依關鍵字猜測。

## 來源快照與更新

- 初次匯入的 `source.md` 完成 normalize 後，須以 Git commit 保存；只有加入暫存區不算保存版本。
- 一般校正只修改 `corrected.md`。使用者明確要求重新匯入來源時，才可更新既有 `source.md`。
- 更新前確認目前磁碟上的 `source.md` 已完整保存於 Git commit；尚未追蹤或有未提交差異時，先保存該檔案的版本，不夾帶無關變更。無法保存時，不覆寫來源。
- 重新匯入仍只執行 normalize，不改寫原文或 Markdown 標記。舊來源由 Git 歷史保存，不新增第三份教材內容檔。
- 來源更新後，重新比對 `source.md`、既有 `corrected.md` 與校正報告，保留仍適用的校正。舊報告的差異、核准敘述及驗證結果不得直接視為新版的完成依據；依受影響內容重新校正、建置與驗證。

## EP62 參考標準與逐份驗收

EP62 核准成品作為清楚指令、固定題型標記、成人語氣與可填答版面的品質參考；不要求其他主題套用其職場內容、四區架構、題數或相同系列標題。版面與建置仍以 [格式契約](FORMAT_CONTRACT.md) 及專案共用模板為準。

每份校正均須逐段對照目前來源與既有 corrected：

- 保留來源既有的學習目標、說明、題目、選項、條件與結語；辨識可沿用的校正，避免重新改寫已合規內容。
- 每題確認「要做什麼、對哪個內容做、答案填在哪裡」清楚；數量與完成條件只在原題已有要求時明示。
- 確認學生版未混入客群障礙標籤、輔導員分析或診斷式解讀。
- 報告以目前來源為基準，只記錄本輪實際變更；不得沿用舊報告中與目前版本不符的差異或核准敘述。
- 來源更新依 [來源快照與更新](#來源快照與更新) 處理。先通過內容審查與 lint，再由既有 Script build、validate；瀏覽器與列印 QA 依 [工作流](../workflow/WORKFLOW.md) 完成，機械檢查通過不等於整體完成。

## 校正輸出

模型只回報實際變更與待確認事項。`reports/EPxx/correction.json` 使用下列結構：

```json
{
  "status": "pass",
  "audience": "目標客群",
  "changes": [
    {"type": "format|content", "location": "段落或題目", "before": "原文", "after": "校正後", "reason": "規則"}
  ],
  "needs_confirmation": []
}
```

若沒有變更，`changes` 使用空陣列；不要用長篇敘述代替差異紀錄。

完成本輪逐段比對並確認報告符合目前檔案後，由 `bind-correction` 加入 `fingerprints.source` 與 `fingerprints.corrected`，每項包含 `path` 與原始檔案位元組的 SHA-256 `sha256`。路徑在專案內時相對於專案根目錄，否則為絕對路徑；不由模型手填雜湊。

綁定指紋不代表內容已核准，不改寫 `status` 或 `needs_confirmation`。舊報告不得只補指紋而省略重新比對；缺少指紋時視為版本未確認，指紋不符時須重新比對差異與核准項目。
